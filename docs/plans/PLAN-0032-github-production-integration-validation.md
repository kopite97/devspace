# Plan: GitHub 배포 환경 통합·Webhook 후속 검증

작성일: 2026-10-20  
상태: `active` — 2026-10-20 사용자 승인으로 배포·실제 통합 검증 시작.
검토일: 2026-10-20 — 배포 식별·복구 경로·재개 기대값과 시험 격리 조건 보완.

## Goal

PLAN-0031에서 구현한 GitHub 연동을 실제 공개 HTTPS 배포 환경에서 검증한다.
main push로 자동 배포한 버전에서 실제 OAuth, 원격 Issue 변경, Webhook 전달,
비동기 Task 반영과 복구를 확인하고 발견한 연동 결함을 수정한다.
로컬·모의 검증과 실제 배포 검증의 증거를 구분한다.

## Scope

- In scope:
  - PLAN-0031 산출물과 필요한 수정의 main 반영, 자동 배포 대기·확인.
  - 공개 origin의 서비스 로그인·GitHub 동의·결과 화면·세션·프록시 검증.
  - 격리 시험 저장소에서 원격 조건 전환·상태 변경·중지 중 변경과 재개.
  - 실제 Webhook 전달·서명 검증·비동기 반영·중복 재전달·누락 복구 확인.
  - 별도 시험 자원이 확보된 경우 조직 승인·권한 철회·재인증·연결 정리 검증.
  - 발견한 프론트 결함 수정, 필요한 백엔드·운영 보완의 구체적 인계.
  - 테스트 설정 복원, 증거와 미실행 항목·재개 조건 기록.

- Out of scope:
  - 일반 사용자 데이터 삭제, 운영 DB 초기화, 서비스 전체 중단을 이용한 장애 주입.
  - GitHub 쓰기 기능을 애플리케이션에 추가하거나 App의 Issues 권한을 쓰기로 확대.
  - 담당자 검색·작업 이력·취소 등 신규 API/기능의 선행 구현.
  - 로컬 터널로 Webhook 수용 검증을 대체하는 작업.
  - 무관한 레거시 테스트 정비와 다른 PLAN 상태 변경.
  - 백엔드 PLAN-0017 자동 완료 처리.

## Changes

### 1. 실행 기준과 시험 자원 확인

1. 승인 후 현재 작업 트리·브랜치·remote와 프론트/백엔드 main을 확인한다.
   PLAN-0031의 미커밋 구현과 증거를 식별하고 이번 배포에 필요한 변경만 검토·커밋한다.
   다른 작업을 일괄 포함하거나 force push하지 않는다.
2. 공개 서비스 URL, 배포된 백엔드 버전, App·설치·선택 저장소·시험 계정을 재조회한다.
   과거 로컬 linkId나 revision을 배포 DB의 식별자로 재사용하지 않는다.
3. 실제 편집 가능한 시험 저장소와 새 프로젝트를 사용한다. 시험 Issue·라벨에는
   실행별 식별자를 붙이고 변경 전 설정·내용·상태를 기록한다.
   기존 `Test-Repo`도 원격 편집 가능 여부와 다른 연결에 미치는 영향을 먼저 확인한다.
   별도 연결만 만들면 같은 저장소를 구독하는 다른 프로젝트가 격리된다고 가정하지 않는다.
4. 조직/보조 계정, 권한 철회 대상, 폐기 가능한 대량 데이터의 가용성을 확인한다.
   자원이 없는 선택 시험은 미실행 사유와 필요한 자원을 먼저 기록한다.
   필수 Webhook 시험 자원이나 접근이 없으면 필수 검증을 완료 처리하지 않는다.
5. 시험 시작 전에 Actions 실행 조회, App delivery 조회/재전달, 비밀을 제외한
   서버 inbox/job 상태 관측 수단을 확보한다. 공개 Swagger를 켜거나 원문 payload를
   내려받는 방법을 전제로 하지 않는다. delivery↔수신↔작업 대응이 API에 없으면
   허용된 운영 로그 또는 읽기 전용 메타데이터 조회로 확인한다.
   관측 수단이 없으면 UI 변경만으로 Webhook 처리 성공을 추정하지 않는다.

### 2. main push와 배포 완료 확인

1. 실행 승인 후 테스트에 필요한 커밋을 main에 push한다. 사용자가 지정한
   자동 배포 방식을 사용하며 같은 범위의 push를 매번 재승인받지 않는다.
   프론트/백엔드는 별도 저장소·workflow이므로 프론트 push가 백엔드를 배포한다고
   가정하지 않는다. 백엔드 변경이 필요한 경우 해당 저장소 지침과 변경 범위를 확인한다.
2. 잠시 기다린 뒤 해당 push SHA의 Actions 실행을 확인한다. queued/running이면
   상태를 주기적으로 조회한다. 고정 대기 시간이 지났다는 이유만으로 검증을 시작하지 않는다.
   실패·취소·시간 초과는 원인을 해결한 뒤 다시 배포하며 실패 버전으로 시험하지 않는다.
3. workflow의 배포 단계·health 결과, 공개 HTTPS 응답, 실제 제공되는 프론트 자산과
   배포된 컨테이너/이미지 정보를 가능한 운영 경로로 대조한다.
   SHA와 실행 URL·완료 시각을 기록하고 이전 캐시나 다른 main 커밋을 시험하지 않도록 한다.
   버전 대응을 확인할 수 없으면 관측 한계를 기록하고 먼저 확인 수단을 확보한다.
   현재 workflow는 checkout SHA로 빌드하지만 앱의 공개 버전 API나 이미지 SHA 라벨을
   보장하지 않는다. Actions의 checkout SHA·배포 완료와 컨테이너 생성 시각/image ID,
   제공 자산을 함께 대조한다. 공개 버전 API를 이번 검증만을 위해 필수 신설하지 않는다.
   시험 중 새 배포가 발생하면 실행 구간을 나누고 기준 버전을 다시 기록한다.
4. 프론트 workflow의 로컬 HTTP 성공만으로 공개 서비스 전체가 정상이라고 판단하지 않는다.
   공개 `/github/connection-result` 직접 접근·새로고침, API 프록시와 로그인까지 확인한다.
5. 수정 후에도 정적 검증→main push→해당 배포 확인→실패 시나리오 재검증 순서를 반복한다.
6. 공개 로그인/API가 깨지면 원격 이벤트 생성을 멈추고 실패 배포의 로그를 확보한다.
   호환되는 수정 또는 문제 변경의 revert 커밋을 main에 반영해 자동 배포·health를
   다시 확인한다. DB 초기화나 무조건적인 과거 이미지 전환을 복구 수단으로 쓰지 않는다.

### 3. 공개 origin·OAuth·Webhook 준비

1. 배포 APP_ORIGIN, 서비스 OAuth 등록 callback, GitHub callback/return,
   Secure cookie, Host/Forwarded-Proto를 공개 origin 기준으로 대조한다.
   `.env`의 로컬 5173/8080 설정을 배포 설정에 복사하지 않는다.
2. 서비스 로그인부터 GitHub 동의·결과 경로까지 실제 브라우저로 왕복한다.
   결과 쿼리만으로 성공 처리하지 않고 account 재조회, 직접 접근·reload,
   로그아웃/재로그인 후 상태를 확인한다.
   PLAN-0031의 로컬 Google callback 복귀 문제와 공개 origin 결과를 따로 기록한다.
   로컬 callback 등록 변경은 공개 검증의 선행 조건으로 삼지 않는다.
3. 실제 수신 경로 `/api/integrations/github/webhooks`가 공개 HTTPS로 도달하며
   배포 서버의 GitHub 기능·worker가 실행되는지 확인한다.
   App의 이벤트 구독·Webhook 활성 상태·설치 권한과 secret 일치를 확인한다.
   secret/PEM/token은 출력하거나 증거에 저장하지 않는다.
   GitHub의 정상 서명 delivery 접수는 양성 경로로 검증한다. 별도 비민감 시험 payload의
   누락/잘못된 서명 요청은 현재 서버 오류 계약대로 거부되고 inbox/job이 생성되지
   않는지 확인한다. 브라우저 세션·CSRF 예외를 다른 API로 확대하지 않는다.
4. 필요한 App 설정 변경은 선택한 시험 범위와 기존 소비자 영향을 확인한 뒤 적용한다.
   App의 Issue 읽기 권한을 유지하며 원격 시험 편집은 사용자의 시험 계정으로 수행한다.
   관리자 접근이 필요한 단계는 구체적인 설정과 대상이 준비된 시점에만 요청한다.

### 4. 실제 이벤트부터 Task까지 검증

1. 배포 프론트에서 계정·저장소 연결, 초기 수집과 선택 가져오기를 확인한다.
   새 source Task의 편집 제한, priority/tag 수정, 보드·통계·overview/Widget을 확인한다.
2. 자동 가져오기 조건을 저장하고 baseline 완료를 관찰한다.
   기존 일치 Issue가 자동 생성되지 않는지 확인한 다음, 별도의 시험 Issue를
   비일치→일치로 변경해 실제 자동 생성과 중복 방지를 확인한다.
3. 연결된 시험 Issue의 제목/본문·라벨·닫기/재개방을 변경하고 서버 계약의
   매핑·closure 사유 및 Task 상태가 일치하는지 확인한다.
   중지 후 원격 변경에서는 수집과 Task 반영 제한을 구분하고,
   재개 뒤 baseline 및 기존 Task 대조를 확인한다. 중지 중 쌓인 신규 일치 후보는
   재개만으로 자동 생성되지 않고 미리보기·명시적 선택 대상이어야 한다.
   재개 baseline 후 새 비일치→일치 전환은 다시 자동 생성 대상이다.
   기존 Task 갱신과 신규 후보 생성을 별개 Issue로 시험한다.
4. 각 이벤트의 GitHub delivery 식별자·이벤트 종류·전달 시각·응답 상태와
   서버 수신/처리 증거·jobId(노출되는 경우)·Task revision·최종 UI를 연결해 기록한다.
   계약에 없는 job↔설정 revision 관계를 만들지 않는다.
   202 수신만으로 Task 반영 성공이라고 기록하지 않는다.
5. 최초 전달 시험에는 수동 sync를 섞지 않는다. 화면은 기존 polling·focus·명시적
   조회 동선으로 갱신한다. 자동 push UI나 SSE가 있는 것처럼 시험하지 않는다.
   원격 이벤트와 정기 수집의 원인이 불명확하면 Webhook 성공의 증거로 쓰지 않는다.
6. 완료된 실제 delivery를 재전달해 Task 중복 생성·상태 역행이 없는지 확인한다.
   현재 [inbox 저장 구현](../../../devspace-back/src/main/java/com/kopite/devspace/github/infrastructure/GitHubWebhookPersistence.java)은
   delivery ID 중복을 무시하며, [수신 서비스](../../../devspace-back/src/main/java/com/kopite/devspace/github/application/GitHubWebhookService.java)는
   이미 접수한 delivery를 다시 처리하도록 초기화하지 않는다.
   중복 재전달의 202를 새 작업 생성이나 실패 작업 복구로 해석하지 않는다.
7. 필수 전달 복구는 **서버에 영속 접수되지 않은 delivery**를 대상으로 한다.
   GitHub의 실패 응답과 inbox 부재를 확인하고 원인을 해소한 뒤,
   같은 실제 delivery 재전달→신규 접수→처리→UI 일치를 검증한다.
   이미 접수됐지만 응답만 유실된 경우는 중복 접수 시험으로 분류한다.
   실패 전달이 없다면 전용 시험 App에서만 잘못된 시험 수신 경로로 한 이벤트를 보내
   실패를 관측하고 정상 경로로 복원한 뒤 재전달하는 방식을 검토한다.
   먼저 다른 설치가 없고 해당 서버에 접수되지 않았음을 확인하며,
   공유 App의 수신 URL·secret 변경이나 공유 서비스 중단으로 장애를 만들지 않는다.
   전용 자원도 기존 실패 delivery도 없으면 이 필수 조건을 미완료로 남긴다.
8. 접수 후 inbox/job 처리 실패는 별도 복구 경로다. 실제 관측된 실패에 대해
   서버의 재시도/backoff·종결 상태와 제공되는 운영 복구 수단을 확인한다.
   같은 delivery 재전달로 재처리를 강제하거나 DB 상태를 직접 초기화하지 않는다.
   수동 sync로 복구했다면 원래 작업의 실패와 새 수집/Task 결과를 별도로 기록한다.
   안전한 처리 실패 주입 자원이 없으면 이 추가 시험은 미실행으로 인계한다.
9. 각 비동기 시험은 시작 시각·관측 종료 기준을 정하고 서버 설정의 재시도/backoff와
   source freshness 대기(계약상 최대 15분)를 고려한다. 짧은 임의 timeout을 결함으로
   단정하거나 무한 대기하지 않는다. 429는 Retry-After를 준수하고 종결 실패·관측 시간
   초과를 구분해 기록한다.

### 5. 추가 실제 수명주기 시험과 정리

1. 확보된 조직/보조 계정으로 설치 승인, 선택 저장소 제외·재추가,
   설치 중단·복구, 사용자 권한 철회와 재인증을 시험한다.
   서버 접근 확인 시간과 상태 전이를 관찰하며 철회 즉시 탐지를 가정하지 않는다.
   원문·편집기·집계 캐시 가림, 일반 Task 유지, 복구 뒤 재조회를 확인한다.
2. 폐기 가능한 데이터에서 일반 Task 전환, 저장소 convert/purge, 계정 교체를 시험한다.
   purge 대상·복원 불가 범위를 명확히 하고 일반 사본 보존 여부를 확인한다.
   50개 초과 시험 데이터가 있으면 해제 진행과 부분 실패/재개를 확인한다.
   실패를 실제로 관찰하지 않았다면 정상 완료만으로 부분 재개를 통과 처리하지 않는다.
3. 접근 거절이나 필요한 계정 부재를 우회하지 않는다. 추가 시험은 자원별로
   성공/실패/미실행과 재개 조건을 기록하고 모의 통과를 실제 통과로 바꾸지 않는다.
4. 시험 설정 enabled/paused/조건/매핑과 원격 Issue·라벨을 원래 의미로 복원한다.
   revision은 되돌리지 않는다. 시험 자원의 보존/정리 결과와 Webhook 최종 활성 상태를
   기록하며 정상 배포에 필요한 Webhook을 시험 종료라는 이유로 끄지 않는다.
5. `docs/reviews/plan0032-github-production-integration-validation/validation.md`에
   배포 SHA·실행 링크·환경·시나리오별 기대/실제·비밀 없는 식별자·복원 결과를 기록한다.
   백엔드 결함은 재현·기대 계약·영향과 함께 인계한다. 수용을 막는 결함이 남으면
   완료하지 않으며 필요한 백엔드 변경은 해당 저장소의 승인된 작업 범위로 처리한다.

## Validation

### Static

- 계획 작성 단계: 템플릿·등록 상태·상대 링크, 변경 Markdown Prettier,
  `npm run check:docs`, `git diff --check`. 런타임 변경이 없어 이 단계에서는 앱 시험을 재실행하지 않는다.
- 실행 전 및 프론트 수정 후: `npm test`, `npm run check:boundaries`,
  `npm run check:queries`, `npm run build`, GitHub 전용 Playwright와 영향받는 현재 회귀.
- 세션/프록시를 수정하면 기존 격리 Vite/Nginx 실제 검증도 재실행한다.
  백엔드 수정 시 해당 저장소 지침에 맞는 테스트·빌드를 수행한다.
- 기존 PLAN-0006~0008 문서 링크 및 레거시 시험 기준선은 분리한다.
  이번 변경의 새 실패를 허용하거나 기존 실패를 전체 통과로 표현하지 않는다.

### Runtime

| 구분      | 필수 검증                                    | 통과 근거                                     |
| --------- | -------------------------------------------- | --------------------------------------------- |
| 배포      | main push 후 대상 버전의 배포 완료·공개 응답 | SHA, Actions 실행과 실제 서비스 대조          |
| 인증      | 공개 서비스 로그인·GitHub 연결·결과 reload   | 실제 provider 왕복과 account 재조회           |
| 기본 연동 | 저장소 연결·import·편집 제한·허용 수정       | job 종결, Task 및 집계/UI 일치                |
| 자동 반영 | baseline, 비일치→일치, 중지 중 변경·재개     | 실제 원격 변경과 서버 계약에 맞는 결과        |
| Webhook   | 실제 전달·서명 처리·비동기 Task 반영         | delivery부터 서버 처리와 최종 UI까지 증거     |
| 복구      | 중복 재전달 및 영속 접수 전 실패 전달 복구   | 중복 없음, inbox 접수 여부 구분, 복구 뒤 일치 |
| 보호·회귀 | 일반 Task·세션·source 편집 제한 유지         | 배포 프론트 관측과 영향받는 회귀              |

조직·철회·계정 교체·파괴적 대량 시험과 접수 후 처리 실패 주입은 별도 자원이 필요한 추가 실제 검증이다.
자원 부족을 구체적으로 기록하면 후속 항목으로 둘 수 있지만, 위 필수 표의 실패/미실행은
배포·Webhook 검증 완료로 처리하지 않는다. 추가 시험에서 발견된 보호/데이터 결함도
해결되지 않은 채 완료하지 않는다. 실제 모바일 기기 검증은 이번 필수 범위가 아니다.

- [ ] 검증 기록과 레지스트리를 갱신하고 백엔드 인계 범위를 명시한다.
