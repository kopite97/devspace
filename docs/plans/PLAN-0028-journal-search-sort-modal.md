# Plan: 개발 일지 검색·필터·정렬 모달 통합

Status: `completed`
Date: 2026-10-13

## Goal

개발 일지 목록(`/journals`)의 검색·필터·정렬 UI를 기본 화면에서 숨기고, 상단의 **`검색 및 정렬` 버튼 하나**로 여는 모달 안에 모두 모은다. 페이지에 들어오면 일지 목록을 바로 볼 수 있고, 필요한 때 모달에서 조건을 조정할 수 있게 한다.

2026-10-13 사용자가 보완된 PLAN-0028을 명시적으로 승인하고 구현 시작을 요청했다. 이 승인을 근거로 `active`로 전환하며, PLAN-0025의 잔여 검증과 다른 계획의 상태는 유지한다.

## Scope

- In scope:

  - 인증된 개발 일지 목록의 검색어, 개발 분야, 프로젝트, 시작일, 종료일, 정렬, 조건 초기화 UI를 같은 모달로 이동.
  - 단일 진입 버튼, 모달의 임시 입력 상태와 적용·취소·초기화 동작, 탐색 허용 여부 전달과 URL 조건 복원.
  - 수정 상세 조회 중 검색 모달 진입 방지 및 화면 이탈 후 도착한 수정 응답의 UI 반영 차단.
  - 키보드 조작, 포커스 복귀, 모바일 배치 및 기존 목록 조회·페이지 추가 로딩 회귀 검증.

- Out of scope:

  - 개발 일지·Document 작성/수정/삭제 및 Viewer 재설계, 새 검색 조건이나 정렬 방식 추가.
  - Home·프로젝트 상세 위젯, 다른 목록 페이지, legacy `JournalWorkspace`의 UI 변경.
  - API 계약, Journal 저장소·캐시 정책, 인증·세션, 공통 Modal 전체의 동작 변경, 신규 의존성 도입.
  - 기존 PLAN-0025의 잔여 검증 수행이나 다른 PLAN의 상태 변경.

## Changes

### 1. 계획 수립 당시 구조와 변경 근거

- [ServerJournalsPage](../../src/pages/ServerJournalsPage.tsx)가 URL의 `category`, `q`, `projectId`, `from`, `to`, `sort`를 읽어 [ApiJournalWorkspace](../../src/features/journal/ApiJournalWorkspace.tsx)에 전달한다.
- `PageScaffold.filters`에 개발 분야·프로젝트·검색어가 있고, 본문 `.journal-query-toolbar`에 날짜·정렬, 그 아래에 초기화 버튼이 있다.
- 검색어는 250ms debounce 후, 나머지 조건은 변경 즉시 URL에 반영된다. `ApiJournalWorkspace`의 key가 `url.pathname + url.search`이므로 조건이 바뀌면 내부 상태와 DOM이 다시 생성된다.
- [AuthApp](../../src/app/auth/AuthApp.tsx)의 `handleNavigate`는 초안 보호 확인에서 취소하면 `false`, 탐색을 허용하면 `true`를 반환한다. 현재 `ServerJournalsPage`와 `ApiJournalWorkspace`의 `onFilterNavigate`는 반환 타입이 `void`여서 이 결과를 모달까지 전달하지 못한다.
- `ApiJournalWorkspace.startEdit`는 상세 조회 완료 후 `memory.editor`를 설정하고 편집 모달을 연다. 현재 응답 반영 조건은 세션 세대만 확인하므로, 검색 모달 진입과 조회 대기 상태의 상호 배제 및 workspace 이탈 여부 확인이 필요하다.
- 현재 `hasFilters`는 정렬을 포함하지 않는다. 모달의 기본값 여부를 판단할 때는 `sort !== 'newest'`도 포함해 정렬만 바꾼 경우를 놓치지 않는다.
- 공통 [Modal](../../src/shared/ui/controls.tsx)은 native dialog, 첫 입력 포커스, Tab 순환, Escape·닫기·배경 클릭, 포커스 복귀를 이미 제공한다. 이 컴포넌트를 재사용한다.

### 2. 화면 구성

1. 개발 일지 heading의 기존 작성 액션 앞에 보조 버튼 `검색 및 정렬`을 하나 추가한다. 검색 아이콘과 텍스트를 함께 표시하고 `aria-haspopup="dialog"`로 모달 진입임을 알린다.
2. 기존 `PageScaffold.filters`, 본문 날짜·정렬 toolbar, 본문의 필터 초기화 버튼을 제거한다. 접힌 영역이나 별도 정렬 버튼을 남기지 않는다.
3. 같은 이름의 모달 안에 아래 컨트롤을 모두 배치한다.

   | 순서 | 컨트롤        | 기본값 / 유지할 선택지                        |
   | ---- | ------------- | --------------------------------------------- |
   | 1    | 검색어        | 빈 문자열, 기존 일지 검색                     |
   | 2    | 개발 분야     | `all`, 미분류 및 기존 분야 옵션               |
   | 3    | 프로젝트      | 전체 프로젝트, 기존 프로젝트 옵션과 보관 표시 |
   | 4    | 시작일·종료일 | 빈 값, 기존 날짜 입력                         |
   | 5    | 정렬          | 최신순(`newest`), 과거순(`oldest`)            |
   | 6    | 하단 액션     | `초기화`, `취소`, `적용`                      |

4. 검색어는 전폭, 분야·프로젝트와 두 날짜는 공간이 충분할 때 2열로 구성한다. 좁은 화면에서는 1열로 전환하고, 정렬과 하단 액션까지 모달 내부에서 접근 가능하게 한다.
5. 적용 조건이 기본값과 다르면 같은 진입 버튼 안에 `적용됨` 표시를 둔다. 페이지 밖으로 필터 칩이나 초기화·정렬 컨트롤을 다시 꺼내지 않는다. 표시 기준은 임시 입력이 아닌 현재 URL의 적용 값이다.
6. 결과 목록, 결과 건수, 로딩·조회 오류·빈 결과 안내와 `더 불러오기`는 목록 영역에 둔다. 기존 `새 글 작성`, `일지 작성` 및 각 행의 동작을 유지한다. 새 글 선택 모달의 검색 안내는 `검색 및 정렬` 버튼명과 일치시킨다.

### 3. 적용·취소·초기화 규칙

- 모달을 열 때 현재 URL에서 전달받은 적용 조건으로 임시 입력 상태를 초기화한다. 임시 입력은 journal feature 안에 두고 모달을 닫으면 폐기한다.
- 입력·선택 변경은 임시 상태만 바꾼다. 기존 검색 debounce와 필드별 즉시 탐색을 모달 입력에 연결하지 않는다. 적용 전에는 URL, 일지 목록 조건, 페이지 커서를 바꾸지 않는다.
- `적용` 또는 검색 입력에서의 Enter 제출은 유효한 조건 전체를 기존 `onFilterNavigate` 경로에 한 번에 전달한다. 모달의 적용 콜백까지 탐색 허용 여부를 `boolean`으로 반환하고, `true`일 때만 모달을 닫는다. 한글 조합 중 Enter를 적용으로 처리하지 않는다.
- 여기서 성공은 URL 탐색이 허용되었다는 뜻이다. 목록 API 응답을 기다렸다가 닫지 않으며, 이후 조회 실패는 기존 목록 오류·재시도 UI로 처리한다.
- 초안 보호 확인에서 사용자가 이동을 취소해 `false`가 반환되면 모달과 임시 입력, 기존 URL·결과·cursor를 유지한다. 포커스를 모달 밖으로 이동하지 않고 적용 후 포커스 복귀 예약을 해제한다. 사용자는 같은 입력으로 다시 적용하거나 모달을 취소할 수 있으며, 검색 폼에서 기존 편집 초안을 지우거나 탐색 보호를 우회하지 않는다.
- 변경 사항이 없으면 모달만 닫고 불필요한 URL 탐색이나 목록 재조회는 일으키지 않는다.
- `취소`, 상단 닫기, Escape, 배경 클릭은 동일하게 임시 입력을 버린다. 이미 적용된 조건과 결과는 유지하며, 다시 열면 적용 값을 보여 준다.
- `초기화`는 모달의 여섯 조건을 기본값으로 되돌리고 모달을 유지한다. `적용`을 눌러야 URL과 목록에 반영되며, 초기화 후 취소해도 기존 적용 조건은 유지한다.
- 시작일이 종료일보다 늦으면 모달에 기존 안내 문구를 표시하고 적용을 막는다. 같은 날짜와 한쪽 날짜만 지정하는 검색은 허용한다. 날짜는 기존 date-only 의미를 유지한다.
- 잘못된 날짜 범위가 담긴 기존 URL로 직접 진입한 경우 필터 없는 결과를 정상 결과처럼 보여 주지 않는다. 목록에는 조건을 수정해야 한다는 상태를 알리고, 동일한 진입 버튼으로 모달을 열어 날짜 오류를 확인·수정할 수 있게 한다.

### 4. URL·조회·포커스 보존

- URL은 적용된 검색 조건의 기준으로 유지한다. 기존 파라미터 이름, 빈 값 제거, legacy `scope` 정리, 기본 최신순 해석을 유지한다. 모달을 열었다는 상태나 임시 입력은 URL에 저장하지 않는다.
- 새로고침, 직접 링크 진입, 뒤로/앞으로 가기 후에도 URL의 조건을 목록에 반영한다. 해당 조건은 모달을 열면 확인할 수 있으며, 탐색으로 떠난 모달의 임시 입력이 뒤늦게 적용되지 않아야 한다.
- 적용 시 모든 조건을 함께 전달해 검색어 변경이 날짜·정렬을 잃거나, 정렬 변경이 검색어·개발 분야·프로젝트를 잃지 않게 한다.
- 기존 `AuthApp.handleNavigate`의 결과를 `PrivateWorkspace` → `ServerJournalsPage` → `ApiJournalWorkspace` → 검색 모달의 적용 콜백으로 반환한다. 페이지와 feature의 콜백 타입 및 반환문에서 `boolean`을 보존하고, 인증·초안 보호 자체의 판단 규칙은 변경하지 않는다.
- 개발 분야와 프로젝트 선택의 기존 조합 규칙을 유지한다. 옵션 목록에 없는 적용 프로젝트를 detail로 보완하는 현재 흐름과 보관 프로젝트 표시를 보존한다. 이번 이동을 계기로 별도의 연동 필터 규칙이나 옵션 API를 추가하지 않는다.
- [JournalStore](../../src/features/journal/apiStore.ts)의 필터 키, `projectStatus: 'all'`, `limit: 20`, cursor 처리와 공유 transport를 그대로 사용한다. 임시 입력으로 목록 조회를 구독하거나 신규 캐시·직접 fetch를 만들지 않는다. 조건을 바꾼 뒤 이전 조건의 cursor를 이어 붙이지 않는다.
- 공통 Modal의 접근성 동작을 재사용한다. 입력별 label, 날짜 오류 연결, 버튼의 포커스 표시를 유지한다.
- URL 적용으로 workspace가 재생성되므로 현재 key를 무작정 제거하지 않는다. `ServerJournalsPage`에서 유지되는 진입 버튼 ref와 이번 적용에 한정한 포커스 복귀 의도를 전달한다. 탐색이 허용되고 해당 URL이 반영된 뒤 새로 생성된 `검색 및 정렬` 버튼에 한 번만 복귀하며, 탐색이 거절되면 복귀 의도를 즉시 해제한다. 일반 페이지 진입이나 브라우저 이력 이동에서는 불필요하게 포커스를 가져오지 않는다.
- 수정 상세 조회가 진행 중인 동안 `검색 및 정렬` 버튼을 비활성화한다. 조회를 시작할 때 동기적으로 기록한 진행 상태를 모달 열기 handler에서도 확인해 연속 클릭으로 우회되지 않게 한다. 검색 모달이 열린 상태에서는 수정 상세 조회를 새로 시작하지 않는다.
- 수정 조회가 성공하면 기존 편집 모달만 열고, 실패하면 기존 오류 안내와 함께 검색 진입 제한을 해제한다. 성공한 편집 모달을 닫은 뒤에도 검색 버튼을 다시 사용할 수 있어야 한다. 검색 모달과 작성·수정·삭제 모달을 중첩해서 열지 않는다.
- 수정 조회 결과는 해당 workspace가 아직 마운트되어 있고 요청이 유효하며 기존 세션 세대 검사를 통과할 때만 `memory.editor`, 편집 열림 상태와 notice에 반영한다. workspace 이탈·재생성 또는 요청 무효화 후 도착한 응답은 이 UI 상태에 반영하지 않는다. 공유 Query/transport를 취소하거나 API를 바꾸는 대신 feature 내부에서 응답 반영 자격을 확인한다.
- 기존 작성 완료 후 필터 초기화 등의 동작은 유지한다. 이번 수정은 탐색 결과 전달과 검색·편집 진입의 조율에 한정한다.

구현 순서:

1. 실행 승인과 registry 순서를 확인하고 `active`로 전환한다. 기존 사용자 변경과 관련 테스트의 현재 기준을 확인한다.
