# Plan: 개발 일지 상세페이지 읽기 중심 재배치

Status: `completed`
Date: 2026-10-13

## Goal

개발 일지 상세(`/journals/:id`)에서 **일지의 맥락을 읽고 연결된 글을 이어서 확인하거나 작성하는 흐름**이 자연스럽도록 화면 전체의 정보 순서와 배치를 재설계한다. 큰 공통 제목 영역과 세로로 분리된 패널을 상세페이지 전용 헤더와 본문·연결 글의 두 영역으로 바꾼다.

사용자가 배치 방향의 판단을 위임하고 PLAN 작성을 요청했다. 2026-10-13 사용자가 보완된 PLAN을 승인하여 구현을 시작했다. PLAN-0028은 `completed`, PLAN-0025의 잔여 검증은 기존 상태로 유지한다.

## Scope

- In scope:
  - 인증된 개발 일지 상세의 헤더, 뒤로 이동, 제목·프로젝트·기록일, 일반 텍스트 본문, 연결된 문서 목록, 새 글 작성 진입 배치.
  - 넓은 화면의 두 열 구성과 모바일 한 열 구성, 긴 콘텐츠 처리, 키보드·포커스, 로딩·오류·빈 목록·추가 로딩 표시.
  - 기능에 맞는 컴포넌트 구성과 Journal 전용 스타일 정리, 관련 회귀 및 실제 인증 화면 검증.
- Out of scope:
  - 개발 일지 목록과 검색 모달, Home·프로젝트 위젯, `/documents/:id` Viewer와 Editor의 UI 재설계.
  - 일지 본문을 BlockNote/Markdown으로 변환하거나 수정·삭제·검색·정렬·드래그·자동 목차 등의 새 기능 추가.
  - API·인증·캐시·cursor·저장 계약 변경, 공통 PageScaffold와 앱 셸의 전역 디자인 변경, 새 의존성 도입.
  - PLAN-0025의 전체 잔여 검증이나 다른 PLAN의 상태 변경.

## Changes

### 1. 코드에서 확인한 현재 구성

- [JournalViewer](../../src/features/journal/JournalViewer.tsx)는 공통 PageScaffold에 제목·일반 안내·`일지 목록` 버튼을 표시한다. 프로젝트와 기록일은 아래 본문 패널 안에 있고, 문서 목록은 본문 다음에 별도 패널로 렌더링된다. 긴 본문 뒤로 문서 목록과 작성 버튼이 밀리는 구조다.
- [JournalDocumentList](../../src/features/journal/JournalDocumentList.tsx)는 `문서` 제목, `새 글 작성`, 문서별 제목·초안/게시됨·수정 시간, 더 불러오기와 건수를 표시한다. 목록은 생성일 최신순이며 표시하는 수정 시간이 정렬 기준인 것은 아니다.
- [CreateDocumentButton](../../src/features/journal/CreateDocumentButton.tsx)은 초안을 만든 뒤 Editor로 이동한다. 생성 중 중복 요청·이탈 방지, 실패 시 결과 확인 안내를 이미 제공한다.
- [ServerJournalViewerPage](../../src/pages/ServerJournalViewerPage.tsx)는 Viewer와 문서 목록을 조합하고, [PrivateWorkspace](../../src/app/auth/PrivateWorkspace.tsx)가 복귀 경로와 Document 탐색을 연결한다. 현재 복귀 경로는 저장된 `documentMemory.returns`가 있으면 사용하고, 없으면 `/journals`이다. 모든 진입에서 목록 필터를 복원한다고 새롭게 가정하지 않는다.
- Journal 본문은 일반 텍스트다. 기존 `.detail-body`의 공백·줄바꿈 표시를 유지해야 한다. 일지 제목은 최대 120자, 본문은 최대 20,000자이므로 짧은 예시만으로 배치를 판단하지 않는다.
- `.journal-viewer`의 margin 규칙 하나가 [Document 스타일](../../src/features/documents/styles.css)에 있다. 상세 전용 스타일을 Journal 영역으로 모으되 Document 본문의 기존 디자인은 보존한다.

### 2. 제안 화면

```text
┌────────────────────────────────────────────────────────┐
│ ← 일지 목록                                새 글 작성  │
│                                                        │
│ 개발 일지 제목                                         │
│ 프로젝트 이름 · 기록일                연결된 글로 이동 │
├─────────────────────────────────┬──────────────────────┤
│ 일지 본문                       │ 연결된 글       8개  │
│                                 │ 생성일 최신순        │
│ 작업 맥락과 기록을 넉넉한        │                      │
│ 행간으로 읽는 주 영역           │ 글 제목              │
│                                 │ 초안 · 수정 일시     │
│                                 │ ──────────────────── │
│                                 │ 글 제목              │
│                                 │ 게시됨 · 수정 일시   │
│                                 │                      │
│                                 │ 더 불러오기          │
│                                 │ ↑ 작성 위치로 이동   │
└─────────────────────────────────┴──────────────────────┘
```

모바일은 **상단 액션 → 제목·메타정보 → 본문 → 연결된 글** 순서다. 긴 본문에서도 헤더의 `연결된 글로 이동`으로 문서 영역에 바로 도달하고, 문서 영역의 `작성 위치로 이동`으로 상단 작성 액션에 돌아올 수 있게 한다.

### 3. 헤더와 액션

1. JournalViewer에 전용 루트와 의미 있는 `header`를 두고 공통 PageScaffold 사용을 이 상세에서만 대체한다. 공통 PageScaffold 자체를 변경하지 않는다. 상세 헤더에서는 반복적인 영문 eyebrow·일반 설명·큰 장식 영역을 줄이고 실제 제목과 메타정보를 먼저 보여 준다.
2. 상단 왼쪽에는 기존 이름의 `일지 목록`, 오른쪽에는 주 액션 `새 글 작성`을 둔다. 좁은 화면에서는 자연스럽게 줄바꿈하고 버튼 간격과 44px 터치 영역을 확보한다. 고정 하단 바나 중복 작성 버튼은 만들지 않는다.
3. `CreateDocumentButton`을 문서 목록에서 헤더 액션으로 옮긴다. ServerJournalViewerPage에서 Viewer의 액션 슬롯으로 조합하고, 같은 일지의 상세 데이터가 있는 동안 한 인스턴스를 유지한다. 생성 활성화는 아래 상세 조회 상태 규칙을 따르며 컴포넌트의 마운트 여부와 분리한다. 목록 컴포넌트의 생성 콜백 책임은 제거한다. 생성 진행·실패 안내는 버튼 가까운 헤더 아래에서 충분한 너비로 표시한다.
4. 제목은 하나의 `h1`이며 여러 줄을 허용한다. 프로젝트명과 기록일은 그 아래 보조 메타정보로 모은다. 프로젝트명을 생략하거나 UUID로 대체하지 않고, 프로젝트 상세 링크 등 새 탐색은 추가하지 않는다. 기록일은 date-only 의미를 유지하고 시간대 변환으로 날짜를 바꾸지 않는다.
5. `연결된 글로 이동`은 API를 호출하지 않는 페이지 내 이동이다. 섹션 제목에 포커스를 옮기고 필요하면 스크롤한다. 기존 경로·query·브라우저 이력은 바꾸지 않으며, 모션 감소 설정에서 강제 부드러운 스크롤을 사용하지 않는다.
6. 문서 영역 하단에는 보조 동작 `작성 위치로 이동`을 둔다. 상단의 기존 `새 글 작성` 버튼으로 스크롤하고 포커스를 옮기기만 하며, 클릭·POST·초안 생성을 대신 실행하지 않는다. 버튼이 생성 진행 또는 생성 오류로 비활성화된 경우에는 진행·오류 안내를 포함한 작성 영역으로 이동하고 해당 영역에 프로그램 방식으로 포커스를 준다. URL·이력·API 요청은 바꾸지 않고 모션 감소 설정을 존중한다. 부모에서 대상 ref와 이동 콜백을 연결해 DOM 전역 검색이나 추가 생성 컴포넌트를 만들지 않는다.

### 4. 본문과 연결된 글

- 화면 전체 콘텐츠 폭은 약 1200px 이내로 정렬한다. 1200px 이상의 viewport에서는 본문 `minmax(0, 1fr)`, 문서 영역 약 280–320px, 간격 24–32px의 두 열을 사용한다. 앱 사이드바를 제외한 실제 공간과 긴 한글 제목을 보고 최종 수치를 조정한다. 그보다 좁으면 한 열로 전환한다.
- 본문은 장식이 적은 `article`로 구성하고 16px 안팎 글자·1.8 전후 행간·읽기 편한 최대 줄 길이를 적용한다. 원문 공백과 줄바꿈을 유지하며 긴 URL·공백 없는 문자열도 가로 overflow 없이 표시한다. HTML로 해석하거나 임의의 문단·코드 블록을 생성하지 않는다.
- 연결 문서는 `연결된 글`이라는 제목의 `section`으로 묶는다. 헤더의 건수는 API `total`을 사용하고, 아직 응답이 없거나 실패한 상태를 `0개`로 표시하지 않는다. `최근 조회 기준` 및 `생성일 최신순` 의미를 보존한다.
- 각 행은 **글 제목 → 상태·수정 일시** 순서로 표현한다. 제목은 최소 두 줄까지 자연스럽게 표시할 수 있는 여유를 주며, 긴 제목도 내용에 따라 줄바꿈한다. 제목 없음은 기존 `제목 없는 문서`를 유지한다. 초안·게시됨은 텍스트로 구별하고 색에만 의존하지 않는다. 수정 일시는 좁은 화면에서 다음 줄로 내려간다.
- 행 전체의 기존 버튼 동작과 Document Viewer 진입을 유지한다. 중첩 버튼·행별 추가 메뉴를 넣지 않는다. 새 글 작성만 기존과 같이 바로 Editor로 이동한다.
- 본문과 문서 영역을 모두 위쪽에 맞춘다. 문서 목록을 높이 고정·별도 스크롤·강제 sticky로 만들지 않아 많은 문서와 확대 화면에서도 페이지 스크롤 하나로 접근한다. 모바일 DOM 읽기 순서도 본문 다음 문서 목록이다.
- 빈 문서 목록은 간결한 안내로 표시한다. 문서 영역 하단의 `작성 위치로 이동`은 빈 목록·문서가 있는 목록·목록 조회 오류에서 공통으로 제공해 긴 본문을 수동으로 거슬러 올라가지 않게 한다. 빈 상태 안에 별도의 생성 컴포넌트나 같은 이동 동작을 중복 추가하지 않는다.

### 5. 상태·접근성·기능 보존

- 초기 상세 로딩과 상세 조회 실패에도 뒤로 이동은 사용할 수 있게 한다. 상세가 없으면 문서 영역·생성 액션을 보여 주지 않는다. 오류와 재시도는 기존 의미를 유지하고 존재하지 않는 일지를 정상 빈 본문으로 표시하지 않는다.
- 상세 조회 상태는 캐시 데이터 유무와 함께 판단한다. 현재 일지의 `state.status === 'ready'`이고 데이터의 ID가 요청 ID와 일치할 때만 생성을 허용한다. 기존 생성 진행·오류에 따른 비활성화 조건도 그대로 적용한다. 이전 데이터가 남은 `idle`·`loading`에서는 새 생성 요청을 막고, `error`에서는 캐시가 남아 있어도 생성 버튼과 문서 영역을 숨긴 채 상세 오류·재시도를 표시한다. 404와 서버 조회 실패 모두 이 규칙을 적용하며, 재시도 성공 후에만 작성 액션을 다시 사용할 수 있다.
- 조회 상태에 따른 노출·활성화 제어와 생성 컴포넌트의 수명을 분리한다. 같은 일지의 데이터가 남아 있는 재조회 중에는 생성 컴포넌트의 key나 위치를 바꾸거나 언마운트하지 않아 진행 중 보호와 불확실한 생성 결과 상태를 보존한다. 상세 재시도 성공도 기존 생성 오류 제한을 임의로 해제하지 않는다. 이 제어는 Viewer에서 상태를 전달해 처리하고 Query의 캐시 보존 정책 자체는 변경하지 않는다.
- 상세와 문서 목록의 상태는 분리한다. 문서 목록 실패가 읽을 수 있는 일지 본문을 숨기지 않으며, 추가 페이지 실패 시 이미 표시한 문서와 기존 재시도 동작을 보존한다. 새 배치에서도 더 불러오기 진행 상태와 버튼 비활성화를 확인한다.
- 생성 진행 중에는 기존 단일 POST·탐색 보호·`초안 만드는 중…`을 유지한다. 생성 결과가 불확실하면 기존 안내와 재생성 제한을 유지하며, 레이아웃 변경·breakpoint 전환 때문에 컴포넌트가 재마운트되어 제한이 풀리지 않게 한다.
- 상세 조회 완료 시 제목에 한 번 포커스를 주는 기존 동작을 보존한다. 문서 추가 로딩·조회 갱신 때 제목으로 포커스를 되돌리지 않는다. 문서 영역 이동 시 `h2`에 프로그램 방식으로 포커스를 주고, 일반 Tab 순서에 불필요한 정지점을 추가하지 않는다.
- 기존 `JournalDocuments.detail/list/more/create`, 조회 키·freshness·세션 격리·무효화 정책은 그대로 사용한다. 건수·메타정보·모바일 배치를 위해 중복 구독이나 추가 API를 만들지 않는다.
- 스타일은 `.journal-detail-*`, `.journal-document-*` 등 상세 전용 selector에 한정한다. 다른 화면에서도 쓰는 `.document-row`, `.content-panel`, `.detail-body`, 공통 헤더·버튼을 전역으로 재정의하지 않는다. 기존 `.journal-viewer .detail-body`의 본문 의미도 유지한다.

## Validation

### Static

- PLAN 작성 단계에서는 번호 0029 유일성, 런타임 템플릿, proposed 등록, 문서 링크·Prettier·`git diff --check`만 확인한다. 앱 구현·빌드·런타임 검증은 실행 승인 후 수행한다.
- 구현 후 `npm run build`(TypeScript·query 검사 포함), `npm run check:boundaries`, `npm run check:docs`, 변경 파일 Prettier와 `git diff --check`를 실행한다. 기존 PLAN-0006~0008의 외부 backend 상대 링크 오류 등 무관한 실패는 구분해 기록한다.
- diff에서 API·Query 정책·생성 보호·복귀 콜백 및 Document Editor/Viewer 스타일이 보존되었는지, 상세 전용 CSS가 목록·다른 페이지를 변경하지 않는지 확인한다.
- 생성 가능 여부를 캐시 데이터 존재만으로 판단하지 않는지, 조회 상태 변경이 생성 컴포넌트를 재마운트하지 않는지 확인한다. 문서 영역의 작성 위치 이동은 기존 버튼 또는 안내 영역만 대상으로 하고 생성 handler를 호출하지 않아야 한다.

- 기존 `npx playwright test --config playwright.journals.config.ts`로 목록·검색 모달·상세 진입·본문 공백 보존 회귀를 확인한다. 기존 fixture가 Document 목록 요청을 abort하는 원칙을 유지하고, 성공한 문서 목록·생성·상세 배치는 실제 API에서 검증한다.
- 기존 `node tests/real/run.mjs --documents`를 활용해 실제 백엔드·격리 DB·OIDC 테스트 세션에서 Viewer·새 초안 생성·Editor 이동·문서 복귀·페이지 추가 로딩을 검증한다. 이전 PLAN의 잔여 전체 작업을 새 완료 기준으로 가져오지는 않는다. 실행 환경의 `BACKEND_ROOT`, Java 21·Docker를 확인하며 실제 사용자 데이터로 생성·삭제 테스트를 하지 않는다.
- 실 API 기반 경계 사례는 기존 도구 안에서 응답 지연·실패를 제어해 검증한다. 성공 데이터를 새 mock 체계로 대체하거나 별도 서버 runner/config를 만들지 않는다.
