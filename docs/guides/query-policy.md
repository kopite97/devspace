# 서버 조회 정책 적용 지침

신규 서버 데이터 조회와 기존 조회 변경 시 사용하는 개발 기준이다.
[PLAN-0022](../plans/PLAN-0022-project-query-cache.md)의 [QueryManager](../../src/shared/http/queryManager.ts)와 `check:queries`가 구현되어 있다. 신규 조회는 인증된 작업실에서 주입받은 manager를 사용한다. 자동 검사는 직접 `new Query` 생성의 명시적 예외 목록을 검사하며 모든 네트워크 우회를 정적으로 증명하는 도구는 아니다.

## 적용 구조

| 계층                       | 책임                                                                                                                  |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `app`의 인증된 작업실 경계 | 세션/작업실 세대당 공통 조회 관리 객체 1개 생성·주입, 포커스 이벤트 연결, 종료 시 일괄 정리                           |
| `shared/http`의 공통 모듈  | 조회 등록·키별 공유, 유효 시간, 강제 조회, 취소, 미사용 회수, 늦은 응답 차단. 기능 이름이나 업무 규칙에 의존하지 않음 |
| 기능 저장소                | 타입이 있는 조회 정의·파서·키·정책 선택, 변경 영향과 무효화 대상 선언                                                 |
| 화면/훅                    | 공통 조회 구독, 사용자 새로고침 요청, 화면별 페이지·스크롤 복원                                                       |

현재 기반은 [PrivateWorkspace](../../src/app/auth/PrivateWorkspace.tsx), [Query](../../src/shared/http/query.ts), [freshTransport](../../src/shared/http/freshTransport.ts)다. 전역 singleton·HTTP 응답 전체 캐시 대신 기존 기반 위에 작은 세션별 조회 등록/생성 모듈을 둔다. 별도 라이브러리나 Provider는 필요성이 확인될 때만 도입한다.

## 새 기능을 만들거나 조회를 변경할 때

1. 서버 상태 조회는 공통 등록/생성 경로를 사용한다. 컴포넌트별 캐시·직접 fetch·독립 Query 생성으로 우회하지 않는다. 구현 전에는 기존 공통 Query/transport를 사용하고 정책 적용 대상을 명시한다.
2. 기능 namespace, 리소스, 모든 응답 결정 조건을 포함하는 안정된 키를 정의한다. 목록과 상세, active/all, 필터·정렬·limit·페이지 표현을 구분한다. 같은 키에 다른 파서나 fetcher를 등록하면 오류로 처리한다.
3. 정책을 타입으로 반드시 선택한다. 프로젝트의 30초/5분은 프로젝트 프로필이며 모든 기능의 고정 기본값이 아니다. 즉시 재검증이 필요한 조회도 공통 경로에서 명시적 정책을 선택한다. 캐시 값은 세션별 메모리에만 보관한다.
4. 재사용 조회와 강제 조회를 구분한다. 화면 이탈은 데이터 변경이 아니며, seed·생성 replay·오래된 본문을 검증 성공으로 취급하지 않는다. 누적 페이지의 만료 기준을 추가 페이지 조회로 연장하지 않는다.
5. 생성/수정/삭제/보관/분류 변경이 영향을 주는 목록·상세·집계·옵션을 기능별로 기록하고 무효화한다. 공통 모듈은 실행을 담당하며 업무상 의존성을 URL만 보고 추론하지 않는다.
6. 인증·CSRF·로그아웃·mutation은 읽기 캐시 대상이 아니다. 기존 transport의 보안·revision·세션 세대 검증과 오류 복구를 유지한다.
7. 재방문, 만료·강제 조회, 저장 후 갱신, 오류·재시도, 세션 교체·늦은 응답을 검증한다. 페이지가 있으면 커서·필터 변경을, 공유 소비자가 있으면 한 소비자 이탈과 회수 경계를 추가한다.

## Document 조회 정책

[DocumentStore](../../src/features/documents/store.ts)와 [JournalDocuments](../../src/features/journal/documentCollection.ts)는 `freshForMs: 0`, `gcAfterMs: 60000`, `revalidateOnFocus: false`를 선언한다. 상세 키에는 UUID, Journal별 문서 목록 키에는 Journal UUID와 limit을 포함하며 추가 페이지는 동일 조회 안의 cursor chain으로 관리한다. 재방문·명시적 새로고침은 다시 읽고 focus는 편집 내용을 교체하지 않는다.

Document 저장·게시·삭제는 문서 상세와 Journal 문서 목록을 무효화한다. Journal 변경은 별도 Viewer projection과 문서 목록도 무효화한다. 같은 PrivateWorkspace manager를 사용하며 세션 종료 때 일괄 취소한다. 회수된 조회 adapter는 재사용하지만 비어 있는 조회의 반복 GC timer는 예약하지 않는다. 기존 Journal CRUD 저장소 전체를 전환하지는 않는다.

## 자동 검사와 예외 관리

- 공통 생성 API는 정책 선언을 필수 인자로 받아 누락을 타입 검사로 막는다. 인증된 작업실에서 주입받은 관리 객체를 사용하며 기능별로 별도 객체를 만들지 않는다.
- `check:queries` 정적 검사는 운영 소스의 직접 Query 생성, 공통 HTTP 경로 밖의 네트워크 호출, 허용되지 않은 저수준 모듈 접근을 검사한다. import 별칭·재수출도 검사 대상으로 한다. 테스트·로컬 도구는 운영 코드와 구분한다.
- `prebuild`에서 검사를 실행하여 로컬/Render의 기존 `npm run build` 경로에 연결한다. 허용/위반 fixture로 검사 자체를 검증한다. CI를 별도로 구성할 때도 같은 명령을 사용한다.
- 기존 미전환 기능은 정확한 파일/호출 지점·이유·담당 TODO를 가진 예외 목록으로 유지한다. 새 위반은 실패시키며 wildcard나 자동 목록 갱신으로 통과시키지 않는다. 기능 전환 시 예외를 제거한다.
- 현재 예외는 [조회 정책 예외 목록](query-exceptions.md)과 [`check:queries`](../../tools/check-queries.mjs)에 동일하게 기록한다. 프로젝트 목록·상세를 다시 직접 `new Query`로 만들면 검사에 실패해야 한다.
- 예외는 인증 bootstrap·외부 SDK 등 캐시 적용이 부적절한 근거와 검증을 함께 검토한다. 지침만으로 모든 우회를 막을 수는 없으며, 정적 검사도 업무상 무효화의 정확성을 증명하지 못하므로 코드 리뷰·회귀 테스트를 병행한다.

## 점진적 적용

PLAN-0022는 공통 경로·검사와 프로젝트를 구현한다. 기존 다른 기능은 정책을 일괄 변경하지 않는다. TODO 03은 선택 데이터, TODO 04는 할 일, TODO 05는 홈을 같은 경로로 검토하며 아직 다루지 않는 일지·마일스톤·링크 저장소 전환은 별도 계획으로 추적한다. 기존 캐시 객체를 adapter가 참조하는 동안 중복 인스턴스를 만들지 않도록 참조·구독·회수 경계를 함께 관리한다.
